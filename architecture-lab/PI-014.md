## 1. Objetivo Geral

Esta Product Interpretation (PI-014) marca a transição oficial da engenharia do Lio Feliz da fase de **consolidação de infraestrutura** para a fase de **evolução funcional do produto**.

O objetivo é transformar o conjunto atual de páginas e features em **módulos funcionais completos e coesos**, reutilizando integralmente a arquitetura existente e eliminando a sensação de funcionalidades isoladas.

Nenhuma Frozen Baseline será alterada. Nenhuma camada congelada será modificada. Toda implementação permanecerá na Presentation Layer, com exceção de melhorias pontuais na Application Layer quando estritamente necessário.

## 2. Motivação

### 2.1 Estado Atual

A plataforma Lio Feliz possui:

- **20 EWOs concluídas** cobrindo Core Foundation, Domain, Application, Infrastructure e Presentation
- **22 módulos de domínio** com BR + Core + Application + Infrastructure
- **18 módulos com Presentation funcional**
- **139 test files, 1091 testes aprovados**
- **Deploy na Vercel** com CI/CD via GitHub Actions
- **Stack oficial:** GitHub + Supabase + Vercel + Sentry

A plataforma é **completa em engenharia** mas ainda **imatura como produto**.

### 2.2 Oportunidades Identificadas

| Oportunidade | Impacto |
|-------------|---------|
| Páginas funcionam de forma isolada, sem navegação integrada entre módulos | UX fragmentada |
| Funcionalidades relacionadas estão dispersas em rotas sem agrupamento | Dificuldade de descoberta |
| Módulos com BR+Core+App+Infra não têm Presentation unificada | Subutilização do potencial |
| Navegação atual não reflete a estrutura de módulos do produto | Curva de aprendizado alta |
| Funcionalidades implementadas em EWOs diferentes não estão integradas entre si | Oportunidade de composição |

## 3. Escopo

### 3.1 Incluído

- Definição da arquitetura de módulos funcionais.
- Reorganização da navegação para modelo modular (baseado em agrupamento de features relacionadas).
- Integração entre funcionalidades atualmente isoladas.
- Criação de páginas-módulo que agrupam funcionalidades relacionadas.
- Melhoria da experiência de navegação com breadcrumbs, tabs internas e visão de contexto.
- Evolução do módulo **Carteira** como modelo de referência para os demais módulos.
- Criação dos módulos **Mercado**, **Proventos**, **Relatórios**, **Ferramentas**.
- Evolução do módulo **Configurações** (unificação de settings esparsos).
- ADRs necessários para cada módulo.
- Testes de arquitetura.
- Atualização documental.

### 3.2 Excluído

- Modificação de qualquer camada congelada (Core Foundation, Domain, Application, Infrastructure).
- Alteração de Core Domain (entidades, VOs, serviços de domínio existentes).
- Alteração de ports existentes.
- Criação de novas regras de negócio.
- Nova arquitetura — reuso máximo do que já existe.
- Vida Financeira (FEAT-006) — escopo grande demais para esta Onda.
- Integração B3 oficial (FEAT-005) — depende de parceria comercial.

## 4. Diretrizes Arquiteturais

### 4.1 Princípios

1. **Reuso máximo, criação mínima.** Todo componente, hook, viewModel e service já existe. A organização em módulos deve **compor** o que existe, não **duplicar**.
2. **Módulo ≠ Pasta nova.** Módulo funcional é um **ponto de entrada na navegação** que agrupa funcionalidades relacionadas. As features continuam em suas pastas atuais em `src/presentation/features/`.
3. **Navegação como arquitetura.** A estrutura do menu principal reflete a organização do produto. Cada entrada do menu é um módulo funcional.
4. **Composição sobre herança.** Módulos reutilizam componentes de outros módulos via importação direta — não por herança ou abstração adicional.

### 4.3 Padrão de Navegação

Cada módulo deve ter:

| Elemento | Descrição |
|----------|-----------|
| **Página principal** | Visão geral do módulo com links para sub-páginas |
| **Navegação interna** | Tabs ou sidebar secundária dentro do módulo |
| **Breadcrumb** | Contexto de navegação (ex: Carteira > Patrimônio) |
| **Estado consistente** | Loading, empty, error states padronizados (reutilizar Skeleton, EmptyState, ErrorState) |

## 5. Diretrizes de UX

### 5.1 Navegação por Módulos

A navegação principal deve ser reorganizada para refletir a estrutura de módulos. Cada entrada do menu principal (Mercado, Carteira, Proventos, Relatórios, Ferramentas, Configurações) representa um módulo funcional.

### 5.2 Sub-navegação Interna

Cada módulo deve fornecer:

- **Tabs** ou **sidebar secundária** para navegação entre sub-páginas
- **Breadcrumb** visível indicando a localização atual (ex: Carteira > Proventos)
- **Título consistente** no topo de cada sub-página

### 5.3 Referência de Usabilidade

O **Investidor10** deve ser utilizado **exclusivamente como referência de organização e fluxo**:

- ✅ Organização em módulos (Carteira, Proventos, etc.)
- ✅ Sub-navegação por tabs
- ✅ Breadcrumbs
- ❌ Não copiar layouts
- ❌ Não copiar identidade visual
- ❌ Não copiar comportamentos específicos

## 6. Estratégia de Implementação

### 6.1 Abordagem

1. **Módulo Carteira como piloto** — já possui a estrutura de sub-páginas mais completa.
2. **Reorganizar navegação** — atualizar SiteHeader e MobileNav para refletir módulos.
3. **Adicionar navegação interna** — breadcrumbs, tabs, visão de contexto.
4. **Expandir para demais módulos** — Mercado, Proventos, Relatórios, Ferramentas, Configurações.

## 12. ADRs Necessários

### ADR-014-001: Módulo Carteira como Piloto

| Campo | Valor |
|-------|-------|
| Contexto | A Carteira é o módulo com mais sub-páginas implementadas (resumo, patrimonio, proventos, rentabilidade, cobertura, analise, lancamentos, metas, IRPF). |
| Decisão | Utilizar a Carteira como piloto para definir o padrão de módulo funcional. O padrão será replicado para os demais módulos. |
| Consequências | O padrão de navegação interna (tabs + breadcrumbs) será definido pela Carteira e reutilizado pelos demais módulos. |

### ADR-014-002: Navegação por Tabs (não Sidebar)

| Campo | Valor |
|-------|-------|
| Contexto | A navegação interna do módulo pode ser feita por tabs (horizontais no topo) ou sidebar (vertical na lateral). |
| Decisão | Utilizar **tabs horizontais** como padrão de navegação interna. A sidebar será reservada para navegação principal do site. Motivo: responsividade mobile (tabs colapsam melhor que sidebar). |
| Consequências | `ModuleTabs` substitui a navegação secundária. `MobileNav` continua como navegação principal inferior. |
