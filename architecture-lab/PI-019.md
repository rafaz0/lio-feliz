## 1. Objetivo Geral

Esta Product Interpretation (PI-019) define a arquitetura da **Plataforma Administrativa e Comercial** do Lio Feliz, estabelecendo os mecanismos de gestão de usuários, planos, assinaturas, permissões, recursos premium e preparação para monetização.

A PI-019 reutiliza integralmente as decisões arquiteturais anteriores (PI-001 a PI-018, ADR-009, ADR-017-001, ADR-017-002, ADR-018-001, ADR-018-002) e expande a plataforma com as camadas administrativa e comercial sem modificar nenhum módulo existente.

---

## 2. Motivação

### 2.1 Estado Atual

A plataforma Lio Feliz possui hoje:

- **PI-018** concluída — 5 perfis de usuário definidos, modo demo funcional, navegação adaptativa.
- **ADR-018-002** aprovado — Perfil Administrador definido como perfil operacional.
- **Zero funcionalidade administrativa** — gestão de usuários, planos e configurações depende de acesso direto ao banco Supabase.
- **Zero modelo de planos** — todos os usuários têm acesso irrestrito a todas as features.
- **Zero controle de assinaturas** — não há mecanismo para planos pagos.
- **Zero recursos premium** — não há diferenciação de acesso por plano.
- **Experience Layer** consolidada — componentes reutilizáveis disponíveis.

### 2.2 Oportunidades Identificadas

| Oportunidade                             | Impacto                                                         |
| ---------------------------------------- | --------------------------------------------------------------- |
| Sem painel administrativo                | Dependência de acesso direto ao banco para tarefas operacionais |
| Sem modelo de planos                     | Impossibilidade de monetizar a plataforma                       |
| Sem controle de assinaturas              | Todos os usuários têm acesso ilimitado                          |
| Sem limites por plano                    | Sem diferencial entre Free e Pro                                |
| Recursos existentes sem proteção premium | Nada impede uso irrestrito                                      |

## 3. Escopo

### 3.1 Incluído

- Definição de Bounded Contexts (Comercial, Assinaturas, Billing, Administração).
- Entidades conceituais (Plan, Subscription, Feature, Permission, Role, AuditLog, UsageCounter).
- Regras arquiteturais (isolamento, mediação, ausência de dependência circular).
- Estratégia de integração com módulos existentes (Auth, Carteira, Gestão Financeira, Dashboard, Demo, Experience Layer).
- Estratégia de persistência (novas tabelas, isolamento por contexto).
- Navegação administrativa (/admin).
- Feature Flags (plano comercial, recursos premium).
- Reuso de Experience Layer.
- Segurança (autorização, permissões, roles, proteção de rotas e server functions).
- Modelo de comercialização (Free, Pro, Enterprise).
- Divisão em EWOs.
- ADRs recomendadas.

### 3.2 Excluído

- Implementação de qualquer funcionalidade.
- Criação de páginas ou componentes.
- Integração com gateways de pagamento.
- Alteração de módulos existentes (Carteira, Gestão Financeira, Dashboard, Auth, Demo).
- Criação de regras de negócio do domínio financeiro.
- Implementação de billing (apenas preparação arquitetural).

## 4. Bounded Contexts

### 4.1 Contextos Definidos

| Contexto          | Responsabilidade                                           | Domínio                     |
| ----------------- | ---------------------------------------------------------- | --------------------------- |
| **Identidade**    | Autenticação, cadastro, roles básicas                      | Core (existente, expandido) |
| **Comercial**     | Planos, features, limites, preços                          | Suporte                     |
| **Assinaturas**   | Controle de assinaturas por usuário, ciclo de vida, status | Suporte                     |
| **Billing**       | Faturamento, cobrança, histórico de pagamentos             | Suporte (preparação)        |
| **Administração** | Gestão de usuários, planos, logs, configurações globais    | Operacional                 |
| **Auditoria**     | Logs de ações administrativas, mudanças de plano           | Suporte                     |

### 4.2 Mapa de Contextos

```
┌─────────────────────────────────────────────────────────────┐
│                     Identidade (existente)                   │
│  Auth, Cadastro, Roles básicas (user, admin)                │
└──────────────────────────┬──────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                     Comercial                                │
│  Planos │ Features │ Limites │ Preços                       │
└──────────┬──────────────────────────┬───────────────────────┘
           │                          │
           ▼                          ▼
┌──────────────────────┐  ┌──────────────────────────┐
│   Assinaturas        │  │   Billing (preparação)   │
│  Por usuário         │  │  Faturamento             │
│  Ciclo de vida       │  │  Histórico               │
│  Status              │  │  Gateway (futuro)        │
└──────────┬───────────┘  └──────────┬───────────────┘
           │                          │
           └──────────┬───────────────┘

┌─────────────────────────────────────────────────────────────┐
│                   Auditoria                                  │
│  AuditLog │ Mudanças de plano │ Ações admin                 │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 Regras de Contexto (R-CTX-019)

| Regra                                                        | Descrição                                                                                                         |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| **R-CTX-019-001** — Comercial não depende de Assinaturas     | O contexto Comercial define planos e features sem conhecer assinaturas individuais.                               |
| **R-CTX-019-002** — Assinaturas não dependem de Billing      | Assinaturas gerenciam ciclo de vida e status. Billing é um contexto separado que apenas consulta assinaturas.     |
| **R-CTX-019-003** — Billing é preparação, não implementação  | O contexto Billing define interfaces e tipos, mas não implementa gateways de pagamento nesta PI.                  |
| **R-CTX-019-004** — Administração é operacional, não domínio | A Administração não possui entidades de negócio próprias. Ela gerencia entidades dos demais contextos.            |
| **R-CTX-019-005** — Auditoria é escrita apenas               | AuditLogs são apenas inseridos. Nunca alterados ou excluídos.                                                     |
| **R-CTX-019-006** — Identidade não é alterada                | O contexto Identidade (Auth existente) não é modificado. Roles administrativas são adicionais, não substitutivas. |

## 5. Entidades Principais

### 5.1 Catálogo de Entidades

| Entidade               | Contexto      | Descrição                                                                                |
| ---------------------- | ------------- | ---------------------------------------------------------------------------------------- |
| **Plan**               | Comercial     | Plano de assinatura (ex: Free, Pro, Enterprise). Define nome, preço, ciclo, features.    |
| **Feature**            | Comercial     | Recurso controlado por plano (ex: relatorio-avancado, api-externa). Identificador único. |
| **PlanFeature**        | Comercial     | Atribuição de uma Feature a um Plan com limite quantitativo (ex: 10 relatórios/mês).     |
| **Subscription**       | Assinaturas   | Assinatura ativa de um usuário em um plano. Contém status, datas, ciclo.                 |
| **SubscriptionEvent**  | Assinaturas   | Eventos do ciclo de vida (criação, renovação, cancelamento, downgrade).                  |
| **Invoice**            | Billing       | Fatura gerada para uma Subscription. Valor, período, status de pagamento.                |
| **PaymentMethod**      | Billing       | Método de pagamento (cartão, boleto, PIX) — apenas armazenamento de referência.          |
| **PaymentTransaction** | Billing       | Transação de pagamento individual. Status, gateway, código de retorno.                   |
| **AdminUser**          | Administração | Visão administrativa de um usuário. Não é entidade separada — é uma projeção.            |
| **AuditLog**           | Auditoria     | Registro imutável de ação administrativa. Who, what, when, context.                      |
| **UsageCounter**       | Comercial     | Contador de uso de um recurso por usuário/período. Para limites de plano.                |
| **Role**               | Identidade    | Papel do usuário (user, admin). Campo em user_metadata ou tabela separada.               |
| **Permission**         | Comercial     | Permissão concedida a uma Role ou Feature. Ação + recurso (ex: "carteira:write").        |

### 5.2 Relacionamentos Conceituais

```
Plan 1──N PlanFeature N──1 Feature
Plan 1──N Subscription N──1 User
Subscription 1──N SubscriptionEvent
Subscription 1──N Invoice
Invoice 1──N PaymentTransaction
User 1──N UsageCounter N──1 Feature
User 1──N AuditLog
User N──M Role
Role N──M Permission
```

### 5.3 Regras de Entidade (R-EN-019)

| Regra                                               | Descrição                                                                                            |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **R-EN-019-001** — Plan imutável em produção        | Planos em produção não podem ter preço ou features alterados. Alterações criam nova versão.          |
| **R-EN-019-002** — Subscription tracking-only       | Assinaturas apenas registram o plano atual. O controle de acesso é feito pelo sistema de permissões. |
| **R-EN-019-003** — AuditLog imutável                | Nenhuma operação de UPDATE ou DELETE é permitida em AuditLog. Apenas INSERT.                         |
| **R-EN-019-004** — UsageCounter resetável por ciclo | Contadores de uso são resetados no início de cada ciclo de faturamento.                              |
| **R-EN-019-005** — Feature granular                 | Features representam recursos atômicos. Não são agrupamentos. O agrupamento é feito pelo Plan.       |

## 6. Regras Arquiteturais

### 6.1 Princípios (R-ARQ-019)

| Regra                                                                    | Descrição                                                                                                                  |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| **R-ARQ-019-001** — Isolamento financeiro-comercial                      | Nenhum domínio financeiro (Carteira, GF) conhece o contexto Comercial. O comercial consulta o financeiro, nunca o inverso. |
| **R-ARQ-019-002** — Administração como fachada                           | A Administração não implementa lógica de negócio. Ela orquestra chamadas aos contextos Comercial, Assinaturas, Auditoria.  |
| **R-ARQ-019-003** — Planos desacoplados de Auth                          | Planos e features não dependem do mecanismo de autenticação. Auth apenas fornece o userId.                                 |
| **R-ARQ-019-004** — Billing desacoplado dos módulos de negócio           | Billing não conhece Carteira, GF ou Dashboard. Ele apenas gerencia transações financeiras da assinatura.                   |
| **R-ARQ-019-005** — Recursos premium por feature flag                    | O acesso a recursos premium é controlado pelo sistema de feature flags (ADR-017-002), não por condicionais espalhadas.     |
| **R-ARQ-019-006** — Alta coesão, baixo acoplamento                       | Cada contexto tem responsabilidade única e se comunica com os demais exclusivamente via mediação (dispatcher/service).     |
| **R-ARQ-019-007** — Ciclo de vida da Subscription gerenciado por eventos | Mudanças de status (ativação, renovação, cancelamento) emitem eventos para os contextos interessados.                      |
| **R-ARQ-019-008** — Limites verificados na Application Layer             | A verificação de limites por plano ocorre na Application Layer (via middleware ou service), não nos componentes de UI.     |

### 6.2 Hierarquia de Acesso

```
Request
  │
  ▼
Route Guard (beforeLoad) — verifica role + feature flag
  │
  ▼
Component (AuthenticatedRoute/AdminRoute) — fallback visual
  │
  ▼
Server Function (middleware) — verifica role + permissão + limite
  │
  ▼
Application Service — executa lógica
  │
  ▼
Domain / Infrastructure — persiste
```

## 7. Integração

### 7.1 Mediação Obrigatória

Nenhum módulo existente se comunica diretamente com os novos contextos. Toda comunicação é mediada por:

1. **Application Services** — orquestram chamadas entre contextos.
2. **Dispatchers** (padrão existente) — queries e commands.
3. **Event Publisher** (InProcessEventPublisher existente) — eventos de domínio.

### 7.2 Integração por Módulo

| Módulo                | Integração                                                                                                                | Mediação                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| **Autenticação**      | Fornece `userId` e `role` para todo o sistema. Nenhuma alteração.                                                         | AuthService existente           |
| **Carteira**          | O contexto Comercial consulta a Carteira para verificar limites (ex: número de ativos). Carteira não conhece o comercial. | Dispatcher → ObterPosicoesQuery |
| **Gestão Financeira** | Mesmo padrão da Carteira. Comercial consulta GF para verificar limites. GF não conhece o comercial.                       | Dispatcher                      |
| **Dashboard**         | Dashboard administrativo exibe dados dos contextos Comercial, Assinaturas, Auditoria.                                     | AdminService                    |
| **Modo Demo**         | Modo Demo não tem plano. Recursos demo são fixos (não configuráveis por plano).                                           | Nenhuma — demo ignora plano     |
| **Experience Layer**  | Componentes de UI reutilizados no admin (KPIGrid, DataTable, ModuleTabs, etc.).                                           | Nenhuma — reuso direto          |

### 7.3 Diagrama de Integração

```
┌─────────────┐     ┌──────────────────┐     ┌──────────────┐
│   Carteira   │     │  Gestão Financeira│     │   Dashboard  │
│  (existente) │     │   (existente)    │     │  (existente) │
└──────┬───────┘     └───────┬──────────┘     └──────┬───────┘
       │                     │                        │
       │   Dispatcher        │   Dispatcher           │  AdminService
       ▼                     ▼                        ▼
┌──────────────────────────────────────────────────────────────┐
│                    Application Layer                          │
│  PlanService │ SubscriptionService │ BillingService           │
│  AdminService │ AuditService │ PermissionService              │
└──────┬───────────────┬────────────────────┬──────────────────┘
       │               │                    │
       ▼               ▼                    ▼
┌──────────┐  ┌──────────────┐  ┌─────────────────────┐
│ Comercial │  │ Assinaturas  │  │ Billing (preparação)│
└──────────┘  └──────────────┘  └─────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│                    Auditoria                                  │
│  (escutada por Application Services, não por domínios)       │
└──────────────────────────────────────────────────────────────┘
```

## 8. Persistência

### 8.1 Estratégia

| Aspecto        | Decisão                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **Banco**      | Supabase PostgreSQL (mesmo banco existente)                                                                              |
| **Esquema**    | Novas tabelas no mesmo schema `public`, prefixadas por contexto: `comercial_*`, `subscription_*`, `billing_*`, `audit_*` |
| **Isolamento** | Contextos diferentes não possuem FK entre si. Apenas referenciam `user_id` (UUID) sem constraint FK.                     |
| **Ownership**  | Cada contexto é dono exclusivo de suas tabelas. Nenhum contexto escreve em tabela de outro contexto.                     |
| **Migrations** | Novas migrations no diretório `supabase/migrations/`                                                                     |
| **Acesso**     | Apenas via repositórios do contexto dono. Nenhum acesso SQL direto entre contextos.                                      |

### 8.2 Tabelas Previstas

| Tabela                       | Contexto    | Descrição                           |
| ---------------------------- | ----------- | ----------------------------------- |
| `commercial_plans`           | Comercial   | Planos de assinatura                |
| `commercial_features`        | Comercial   | Catálogo de features                |
| `commercial_plan_features`   | Comercial   | Atribuição feature→plano com limite |
| `subscription_subscriptions` | Assinaturas | Assinaturas ativas                  |
| `subscription_events`        | Assinaturas | Eventos do ciclo de vida            |
| `billing_invoices`           | Billing     | Faturas geradas                     |
| `billing_payment_methods`    | Billing     | Métodos de pagamento                |
| `billing_transactions`       | Billing     | Transações individuais              |
| `audit_logs`                 | Auditoria   | Logs de ações administrativas       |
| `commercial_usage_counters`  | Comercial   | Contadores de uso por usuário       |

### 8.3 Regras de Persistência (R-PER-019)

| Regra                                          | Descrição                                                                                                   |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **R-PER-019-001** — Sem FK entre contextos     | Nenhuma chave estrangeira cruza limites de contexto. Apenas `user_id` como UUID livre.                      |
| **R-PER-019-002** — Owned pelo contexto dono   | Cada contexto gerencia exclusivamente suas tabelas. Leituras de outros contextos usam repositórios do dono. |
| **R-PER-019-003** — AuditLog sem UPDATE/DELETE | A tabela `audit_logs` aceita apenas INSERT. Nenhuma trigger ou política de update.                          |
| **R-PER-019-004** — Versionamento de plano     | Alterações em planos criam nova versão (nova linha), não atualizam a existente.                             |

## 9. Navegação

### 9.1 Rotas Administrativas

```
/admin                        → Dashboard administrativo (KPIs, resumo)
/admin/usuarios               → Lista de usuários + busca + detalhes
/admin/planos                 → CRUD de planos e features
/admin/assinaturas            → Assinaturas ativas + histórico
/admin/logs                   → Audit logs
/admin/configuracoes          → Configurações globais (feature flags, limites)
```

### 9.2 Proteção de Rotas

| Camada                 | Mecanismo                                                            |
| ---------------------- | -------------------------------------------------------------------- |
| **Rota**               | `beforeLoad` verifica `user.role === "admin"` + `ADMIN_ENABLED` flag |
| **Componente**         | `AdminRoute` wrapper (similar a `AuthenticatedRoute`)                |
| **Layout**             | `ModuleLayout` com tabs administrativas                              |
| **404 para não-admin** | Usuários não-admin recebem 404 ao acessar `/admin`                   |

### 9.3 Navegação no Header

| Perfil        | Header                                      |
| ------------- | ------------------------------------------- |
| Usuário comum | Sem link admin                              |
| Administrador | Link "Admin" no dropdown de usuário + badge |

## 10. Feature Flags

### 10.1 Novas Flags (estendendo ADR-017-002)

| Flag               | Ambiente | Perfil        | Descrição                            |
| ------------------ | -------- | ------------- | ------------------------------------ |
| `ADMIN_ENABLED`    | Produção | Administrador | Ativa painel admin (ADR-018-002)     |
| `BILLING_ENABLED`  | Produção | Administrador | Ativa módulo de billing (preparação) |
| `PREMIUM_FEATURES` | Produção | Usuário       | Libera recursos premium por plano    |
| `FREE_PLAN_LIMITS` | Todos    | Usuário       | Aplica limites do plano Free         |

### 10.2 Resolução de Acesso a Recurso

```
1. Usuário autenticado? Se não → recurso bloqueado
2. ADMIN_ENABLED + role admin? → acesso total
3. DEMO_MODE? → acesso demo (limites fixos)
4. Usuário tem Subscription ativa? → verificar plano
5. Feature disponível no plano? → acesso liberado
6. UsageCounter dentro do limite? → acesso liberado
7. Recurso bloqueado
```

## 12. Segurança

### 12.1 Mecanismos de Autorização

| Camada              | Mecanismo                       | Onde              |
| ------------------- | ------------------------------- | ----------------- |
| **Role**            | `user_metadata.role`            | Supabase Auth     |
| **Rota**            | `beforeLoad` + `AdminRoute`     | TanStack Router   |
| **Server Function** | Middleware `requireAdmin`       | TanStack Start    |
| **Feature**         | `canAccess(featureId, userId)`  | PermissionService |
| **Limite**          | `checkLimit(featureId, userId)` | PlanService       |

### 12.2 Estrutura de Permissões

```typescript
interface Permission {
  action: string; // "read" | "write" | "admin"
  resource: string; // "carteira" | "relatorios" | "api"
}

interface Role {
  name: string; // "user" | "admin"
  permissions: Permission[];
}

// Exemplo de permissão do plano Pro
const PRO_PERMISSIONS: Permission[] = [
  { action: "read", resource: "carteira" },
  { action: "write", resource: "carteira" },
  { action: "read", resource: "relatorios-avancados" },
  { action: "read", resource: "api-exports" },
];
```

### 12.3 Regras de Segurança (R-SEC-019)

| Regra                                                  | Descrição                                                                                                                               |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| **R-SEC-019-001** — Role no token                      | A role do usuário é obtida do token Supabase (user_metadata), não de uma query separada.                                                |
| **R-SEC-019-002** — Server function verifica permissão | Nenhuma server function administrativa confia apenas no beforeLoad. Cada função verifica a role.                                        |
| **R-SEC-019-003** — Sem auto-admin                     | Nenhuma rota ou função permite auto-atribuição de role admin. Alteração apenas via Supabase console ou função administrativa protegida. |
| **R-SEC-019-004** — Feature check no servidor          | Verificações de acesso premium são feitas no servidor, nunca apenas no cliente.                                                         |
| **R-SEC-019-005** — Rate limiting por endpoint admin   | Endpoints administrativos possuem rate limiting para prevenir abuso.                                                                    |

## 13. Comercialização

### 13.1 Modelo de Planos

| Aspecto                  | Free       | Pro          | Enterprise (futuro) |
| ------------------------ | ---------- | ------------ | ------------------- |
| **Preço**                | R$ 0       | R$ 29,90/mês | Sob consulta        |
| **Ativos na carteira**   | Até 10     | Ilimitado    | Ilimitado           |
| **Relatórios avançados** | ❌         | ✅           | ✅                  |
| **Exportação de dados**  | ❌         | ✅ (CSV)     | ✅ (CSV + API)      |
| **Metas financeiras**    | Até 3      | Ilimitado    | Ilimitado           |
| **Gestão Financeira**    | ❌         | ✅           | ✅                  |
| **API de dados**         | ❌         | ❌           | ✅                  |
| **Suporte**              | Comunidade | Email        | Prioritário         |
| **Usuários**             | 1          | 1            | Até 10              |

### 13.2 Ciclo de Vida da Assinatura

```
Trial (opcional)
  │
  ▼
Active
  │
  ├──→ Canceled (fim do período atual)
  │
  ├──→ PastDue (pagamento falhou)
  │       │
  │       └──→ Canceled (após período de carência)
  │
  └──→ Expired (fim do período sem renovação)
```

### 13.3 Regras Comerciais (R-COM-019)

| Regra                                                 | Descrição                                                                                        |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **R-COM-019-001** — Free é o plano padrão             | Todo novo cadastro inicia no plano Free.                                                         |
| **R-COM-019-002** — Downgrade não destrói dados       | Ao fazer downgrade, dados que excedem o limite do plano Free são preservados mas não acessíveis. |
| **R-COM-019-003** — Upgrade imediato                  | O upgrade para Pro é imediato. O período de faturamento começa na data do upgrade.               |
| **R-COM-019-004** — Cancelamento no fim do ciclo      | O cancelamento não é retroativo. O acesso continua até o fim do período pago.                    |
| **R-COM-019-005** — Limites por recurso, não por tela | Cada recurso premium tem seu próprio limite (ex: número de ativos, relatórios/mês).              |
