## 1. Objetivo Geral

Esta Product Interpretation (PI-017) define a arquitetura do módulo de **Gestão Financeira** da plataforma Lio Feliz.

A Gestão Financeira é um novo domínio que representa a vida financeira completa do usuário — contas bancárias, receitas, despesas, dívidas, financiamentos e patrimônio global — sem substituir ou modificar a Carteira de Investimentos existente.

Ela atua como um **domínio complementar opcional**, integrando-se à Carteira apenas quando explicitamente ativada pelo usuário, sem jamais criar dependência obrigatória.

A PI-017 preserva integralmente as decisões arquiteturais anteriores (PI-001 a PI-016) e estabelece a baseline para as EWOs de implementação da Gestão Financeira.

---

## 2. Motivação

### 2.1 Estado Atual

A plataforma Lio Feliz possui um módulo consolidado de Carteira de Investimentos que gerencia posições, proventos, rentabilidade, IRPF, rebalanceamento e cobertura. O Dashboard funciona como Hub Central.

Usuários da plataforma, no entanto, gerenciam seus investimentos dentro de um contexto financeiro mais amplo que inclui contas bancárias, salários, despesas mensais, dívidas e financiamentos. Sem essa visão, a Carteira opera isolada do resto da vida financeira do usuário.

### 2.2 Oportunidades Identificadas

| Oportunidade | Impacto |
|-------------|---------|
| Carteira opera sem contexto financeiro mais amplo | Usuário não vê o impacto dos investimentos no patrimônio total |
| Origem dos recursos das compras não é rastreável | Perda de informação sobre fluxo financeiro |
| Patrimônio líquido real (com dívidas e imóveis) não é calculado | Visão financeira incompleta |
| Experiência fragmentada entre investimentos e finanças | Usuário precisa de ferramentas externas |
| ADR-009 já aprovou a separação de domínios | Base arquitetural já estabelecida |
| PERSONAL_FINANCE_ARCHITECTURE.md já documenta a visão geral | Arquitetura conceitual pronta para detalhamento |

### 2.3 Marco de Transição

```
PI-015/016 (Ondas 9-10)                  →     PI-017 (Onda 11+)
─────────────────────────────────────────────
Product Evolution + Experience Layer     →     Gestão Financeira
Navegação e UX                           →     Domínio complementar
Dashboard Hub                            →     Patrimônio Global
```

## 4. Princípios Arquiteturais

### 4.1 Princípios da PI-017 (R-PF)

| Regra | Descrição | Origem |
|-------|-----------|--------|
| **R-PF-001** — Separação entre Investimentos e Finanças Pessoais | Carteira e Gestão Financeira são domínios distintos, com bounded contexts, modelos de dados e responsabilidades próprias. | ADR-009 |
| **R-PF-002** — Sincronização Opcional | A integração entre os domínios é sempre opt-in. O usuário decide se deseja ou não conectar sua Carteira à Gestão Financeira. | ADR-009 |
| **R-PF-003** — Ausência de Dependência Obrigatória | Nenhuma funcionalidade da Carteira pode depender de dados da Gestão Financeira. | ADR-009 |
| **R-PF-004** — Rastreabilidade Completa | Toda movimentação financeira deve ser rastreável: origem → destino. | ADR-009 |
| **R-PF-005** — Evolução Incremental | Implementação em ondas: contas/caixa → receitas/despesas → patrimônio global. | ADR-009 |
| **R-PF-006** — Preservação da Carteira | A Carteira permanece como módulo central. A Gestão Financeira a complementa, não a substitui. | ADR-009 |
| **R-PF-007** — Baixo Acoplamento | A Gestão Financeira se comunica com a Carteira exclusivamente através de uma camada de sincronização opcional. Nenhum componente de um domínio importa diretamente componentes do outro. | PI-017 |
| **R-PF-008** — Alta Coesão Interna | Cada sub-módulo da Gestão Financeira (Contas, Caixa, Receitas, Despesas, Dívidas, Patrimônio Global) é coeso e responsável por um conjunto específico de funcionalidades. | PI-017 |

### 4.2 Preservação da Arquitetura Existente

- Nenhuma Frozen Baseline será alterada.
- Nenhuma camada congelada será modificada.
- A Carteira continua funcionando integralmente sem a Gestão Financeira (R-PF-003).
- O Dashboard existente não é modificado — a Gestão Financeira adiciona novos blocos quando ativada.
- A Experience Layer existente é reutilizada para novos componentes.

## 5. Limites de Contexto (Bounded Contexts)

### 5.1 Contextos Existentes (não modificados)

| Contexto | Responsabilidade | Domínio |
|----------|-----------------|---------|
| **Carteira** | Investimentos, proventos, rentabilidade, IRPF, rebalanceamento, cobertura, metas | Investimentos |
| **Dashboard** | Hub central, KPIs, insights, atalhos, navegação | Transversal |
| **Experience Layer** | Componentes reutilizáveis de UX | Presentation |
| **Mercado** | Cotações, ativos, rankings, comparador | Dados de mercado |

### 5.2 Novos Contextos (Gestão Financeira)

| Contexto | Responsabilidade | Domínio |
|----------|-----------------|---------|
| **Contas** | Múltiplas contas bancárias, saldos por instituição | Finanças Pessoais |
| **Caixa** | Saldo disponível consolidado, movimentações de entrada/saída | Finanças Pessoais |
| **Receitas** | Salários, freelas, rendimentos externos, categorização | Finanças Pessoais |
| **Despesas** | Despesas fixas/variáveis, categorização, centros de custo | Finanças Pessoais |
| **Dívidas** | Cartão de crédito, empréstimos, parcelamentos | Finanças Pessoais |
| **Patrimônio Global** | Consolidação Carteira + Caixa + Imóveis + Passivos | Finanças Pessoais |

### 5.3 Limites entre Contextos

```
┌─────────────────────────────────────────────────────┐
│                   Carteira                           │
│  (investimentos, proventos, IRPF, rebalanceamento)   │
└────────────────────┬────────────────────────────────┘
                     │ Sincronização Opcional (R-PF-002)
┌────────────────────▼────────────────────────────────┐
│              Gestão Financeira                       │
│  ┌──────┐ ┌──────┐ ┌────────┐ ┌─────────┐ ┌──────┐ │
│  │Contas│ │Caixa │ │Receitas│ │Despesas │ │Dívidas│ │
│  └──────┘ └──────┘ └────────┘ └─────────┘ └──────┘ │
│                        │                            │
│              ┌─────────▼──────────┐                  │
│              │ Patrimônio Global  │                  │
│              └────────────────────┘                  │
└─────────────────────────────────────────────────────┘
```

### 5.4 Regras de Limite

| Regra | Descrição |
|-------|-----------|
| Nenhum contexto da Gestão Financeira importa da Carteira | Isolamento total |
| A Carteira não importa nenhum contexto da Gestão Financeira | Independência |
| A sincronização entre domínios ocorre via uma camada de integração opcional | Baixo acoplamento |
| Cada contexto da Gestão Financeira é independente entre si | Alta coesão |

## 6. Módulos

### 6.1 Contas

- Múltiplas contas bancárias por usuário.
- Saldo atual, instituição, tipo (corrente, poupança, investimento).
- Histórico de saldos ao longo do tempo.

### 6.2 Caixa

- Saldo disponível consolidado (soma de todas as contas).
- Movimentações de entrada e saída.
- Origem das movimentações: receita, venda de ativo, transferência.
- Integração com origem de recursos na Carteira (quando ativada).

### 6.3 Receitas

- Registro de receitas recorrentes e eventuais.
- Categorização: salário, freela, rendimento, outros.
- Previsão de receitas futuras.

### 6.4 Despesas

- Registro de despesas fixas e variáveis.
- Categorização: moradia, alimentação, transporte, lazer, etc.
- Comparação com proventos da Carteira (cobertura).

### 6.5 Dívidas

- Cartão de crédito: fatura atual, limite, vencimento.
- Empréstimos: saldo devedor, parcelas, taxa de juros.
- Financiamentos: saldo devedor, parcelas, indexador.

### 6.6 Patrimônio Global

- Cálculo: PL = (Caixa + Carteira + Imóveis + Outros Ativos) - (Dívidas + Financiamentos + Passivos).
- Indicadores: patrimônio líquido, patrimônio bruto, evolução temporal.
- Integração com Dashboard (quando ativada): bloco de Patrimônio Global.

## 7. Modelo Conceitual

### 7.1 Entidades Conceituais

```
BankAccount
  ├── id, name, institution, type, balance, currency
  └── Transaction[]
      ├── id, date, amount, type (credit/debit), category
      └── source (income, sale, transfer, external)

Income
  ├── id, description, amount, date, recurrence
  └── category (salary, freelance, investment, other)

Expense
  ├── id, description, amount, date, dueDate, paidAt
  └── category (housing, food, transport, leisure, health, other)

Debt
  ├── id, type (credit_card, loan, financing)
  ├── totalAmount, outstandingBalance, monthlyPayment
  └── interestRate, dueDate

GlobalWealth
  ├── cash: sum of BankAccount balances
  ├── portfolio: from Carteira (read-only)
  ├── realEstate: estimated value
  ├── otherAssets: estimated value
  ├── debts: sum of Debt.outstandingBalance
  └── netWorth: (cash + portfolio + realEstate + other) - debts
```

### 7.2 Relacionamentos

- **Caixa** é a soma de todas as **Contas** (visão consolidada).
- **Patrimônio Global** consolida **Caixa** + **Carteira** (leitura) + **Dívidas**.
- **Despesas** podem ser comparadas com proventos da **Carteira** para cálculo de cobertura.
- **Receitas** alimentam o **Caixa** (entrada).
- **Dívidas** reduzem o **Patrimônio Líquido**.

## 8. Integração com Carteira

### 8.1 Arquitetura de Integração

A integração entre Gestão Financeira e Carteira segue o padrão de **sincronização opcional** definido pelo ADR-009:

```
Carteira (domínio existente)                Gestão Financeira (novo domínio)
─────────────────────────────               ─────────────────────────────────
Operações de compra/venda      ───(sync)──→  Caixa (débito/crédito)
Posição consolidada            ───(sync)──→  Patrimônio Global (leitura)
Proventos recebidos            ───(sync)──→  Caixa (crédito)
                                              │
                                              └── Apenas quando integração
                                                  ativada (feature flag)
```

### 8.2 Comportamento por Estado

| Estado | Comportamento |
|--------|---------------|
| **Integração desativada** (padrão) | Carteira funciona exatamente como hoje. Nenhum dado financeiro é lido ou escrito. A Gestão Financeira não aparece na navegação. |
| **Integração ativada** | Ao registrar compra, usuário informa origem do recurso. Carteira sincroniza posição com Patrimônio Global. Dashboard exibe bloco de Patrimônio Global. |

### 8.3 Camada de Sincronização

A sincronização é feita através de uma camada dedicada:

```
┌──────────────────────────────────────────────┐
│          FinanceIntegrationService             │
│  (opt-in, ativado por feature flag)           │
│                                               │
│  - onBuyOperation(operation, source)          │
│  - onSellOperation(operation, destination)    │
│  - onDividendReceived(dividend)              │
│  - syncPortfolioToGlobalWealth(portfolio)    │
│  - getGlobalWealth() → GlobalWealthView      │
└──────────────────────────────────────────────┘
```

### 8.4 Isolamento

- A camada de sincronização é o **único ponto de contato** entre os domínios.
- Nenhum componente da Carteira importa módulos da Gestão Financeira.
- Nenhum componente da Gestão Financeira importa módulos da Carteira.
- A camada de sincronização só é carregada quando a feature flag está ativa.

## 9. Feature Flags

### 9.1 FinanceIntegrationEnabled

```typescript
interface FinanceIntegrationConfig {
  enabled: boolean;               // Ativado/desativado (padrão: false)
  autoSync: boolean;              // Sincronizar automaticamente
  includeInvestments: boolean;    // Incluir carteira no PL
  defaultIncomeSource: IncomeSource; // Origem padrão para compras
}

type IncomeSource = "cash" | "bank_account" | "asset_sale" | "external_income" | "other";
```

### 9.2 Comportamento

| Estado | Navegação | Dashboard | Operações | Persistência |
|--------|-----------|-----------|-----------|-------------|
| **Desativado** | Gestão Financeira oculta | Bloco PL não exibido | Sem origem de recursos | Nenhum dado financeiro |
| **Ativado** | Gestão Financeira visível | Bloco PL exibido | Origem de recursos disponível | Dados financeiros sincronizados |

## 10. Persistência

### 10.1 Organização dos Dados

A Gestão Financeira utiliza tabelas no banco Supabase, isoladas das tabelas da Carteira:

```
Tabelas da Carteira (existentes)         Tabelas da Gestão Financeira (novas)
───────────────────────────────           ─────────────────────────────────────
portfolio_operations                     finance_accounts
portfolio_projections                    finance_transactions
portfolio_goals                          finance_incomes
...                                      finance_expenses
                                         finance_debts
                                         finance_global_wealth
```

### 10.2 Isolamento

- Nenhuma tabela da Carteira é modificada.
- Nenhuma tabela da Gestão Financeira referencia diretamente tabelas da Carteira.
- A sincronização entre domínios é feita via application services, não via foreign keys.
- Cada domínio possui seus próprios repositórios e projeções.

### 10.3 Compatibilidade com DEV_MODE

A Gestão Financeira respeita a flag `DEV_MODE`:

| Ambiente | Comportamento |
|----------|---------------|
| `DEV_MODE=true` | Dados armazenados em memória (DEV_STORE) |
| `DEV_MODE=false` | Dados armazenados no Supabase |

## 12. Estados da Aplicação

### 12.1 Estados do Módulo

| Estado | Descrição | Comportamento |
|--------|-----------|---------------|
| **Não configurado** | Nenhuma conta cadastrada, integração desativada | Gestão Financeira não aparece na navegação |

## 14. ADRs Necessários

### ADR-017-001 — Camada de Sincronização Dedicada

| Campo | Valor |
|-------|-------|
| Contexto | Gestão Financeira e Carteira são domínios independentes. A comunicação entre eles precisa de um ponto de contato único e controlado. |
| Decisão | Criar `FinanceIntegrationService` como única camada de sincronização entre domínios. Nenhum componente de um domínio importa diretamente o outro. |
| Consequências | Baixo acoplamento, facilidade de teste, possibilidade de desligar integração sem impacto. |

### ADR-017-002 — Feature Flag como Controle de Integração

| Campo | Valor |
|-------|-------|
| Contexto | A integração entre Carteira e Gestão Financeira deve ser opcional e controlada pelo usuário. |
| Decisão | Utilizar feature flag `FinanceIntegrationEnabled` (armazenada em configuração do usuário) para controlar visibilidade e funcionalidade do módulo. |
| Consequências | Quando desativada, zero overhead. Quando ativada, carregamento condicional da camada de sincronização. |
