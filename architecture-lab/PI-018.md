## 1. Objetivo Geral

Esta Product Interpretation (PI-018) define a arquitetura para os diferentes modos de utilização da plataforma Lio Feliz, consolidando os perfis de usuário, ambientes de execução e mecanismos de demonstração.

A PI-018 estabelece como a plataforma se comporta em cada modo (Demo, Desenvolvimento, Produção), como cada perfil (Visitante, Usuário, Demo, Desenvolvedor, Administrador) interage com o sistema, e como Feature Flags controlam a experiência por ambiente.

Ela reutiliza integralmente as decisões arquiteturais anteriores (PI-001 a PI-017, ADR-009, ADR-017-001, ADR-017-002) e prepara o terreno para funcionalidades comerciais e de validação.

---

## 2. Motivação

### 2.1 Estado Atual

A plataforma Lio Feliz possui hoje:

- **APPLICATION_STATES.md** (v2.0) que descreve conceitualmente 5 perfis (Visitante, Demo, Usuário, Desenvolvedor, Administrador), mas sem definição arquitetural formal.
- Um mecanismo de **DEV_USER** implementado inline em `route.tsx`, `use-session.ts` e `auth-middleware.ts`, sem arquitetura definida.
- **Feature Flags** formalizadas no ADR-017-002, mas apenas para integração Carteira/Gestão Financeira.
- Processo de **login** que redireciona para `/dashboard`, sem suporte a modo demo.
- **Sem modo administrador** — não existe rota, layout ou permissão administrativa.

### 2.2 Oportunidades Identificadas

| Oportunidade | Impacto |
|-------------|---------|
| Ausência de modo demo | Dificuldade de conversão de visitantes |
| DEV_USER implementado sem arquitetura | Risco de regressão em produção |
| Sem admin para gerenciar usuários | Dependência de acesso direto ao banco |
| Feature Flags apenas para um domínio | Falta de estratégia unificada |
| Perfis documentados mas não arquitetados | Lacuna entre documentação e código |

### 4.3 Regras de Perfil (R-PF-018)

| Regra | Descrição |
|-------|-----------|
| **R-PF-018-001** — Perfil isolado por sessão | Cada perfil opera em contexto de dados isolado. Dados demo nunca se misturam com dados reais. |
| **R-PF-018-002** — Leitura apenas para Demo | O perfil Demo não pode criar, alterar ou excluir dados. Operações de escrita são simuladas. |
| **R-PF-018-003** — Admin como leitor de todos os domínios | O Administrador pode ler dados de qualquer usuário, mas não pode modificá-los sem autorização explícita. |
| **R-PF-018-004** — Perfil determinado por autenticação | O perfil é definido no momento da autenticação/autorização e não pode ser alterado pelo usuário. |

## 5. Modos

### 5.1 Modo Demo

**Arquitetura:**

```
Visitante clica "Experimentar"
  → Sessão demo criada (sem cadastro)
  → Dados seed carregados em memória
  → Todas as rotas autenticadas ficam acessíveis
  → Operações de escrita são simuladas (sem persistir)
  → Sessão expira após período configurado
```

**Características:**

| Aspecto | Comportamento |
|---------|---------------|
| Ativação | Botão "Experimentar" na Home ou `/login` |
| Sessão | LocalStorage/memória, sem Supabase |
| Dados | Seed data pré-definido (carteira, movimentações, metas) |
| Escrita | Simulada — dados voltam ao estado original ao recarregar |
| Expiração | 30 minutos de inatividade ou 24h no total |
| Isolamento | Nenhum dado real é acessado ou modificado |

**Dados de Seed (previstos):**

- Carteira com 5-8 ativos (ações + FIIs)
- Histórico de 12 meses de operações
- Proventos recebidos
- Metas financeiras
- Gestão Financeira com contas, receitas e despesas

### 5.2 Modo Desenvolvedor

**Mecanismo existente (a ser formalizado):**

| Componente | Função atual |
|-----------|-------------|
| `isLocalDev()` em `route.tsx` | Detecta localhost |
| `DEV_USER` em `use-session.ts` | Usuário mock |
| `DEV_STORE` em `operations.functions.ts` | Store em memória |
| `DEV_MODE` flag | Controle de persistência |

**Arquitetura proposta:**

```
DEV_MODE=true (env) + localhost
  → Auth bypass automático
  → DEV_STORE para dados voláteis
  → Logs detalhados
  → Hot reload de dados seed
```

### 5.3 Modo Administrador

**Arquitetura prevista:**

```
Usuário com role "admin"
  → Rota /admin acessível
  → Painel com:
    - Usuários cadastrados
    - Planos e assinaturas
    - Logs do sistema
    - Configurações globais
  → Leitura de dados de qualquer usuário
  → Sem escrita em dados de usuário (apenas suporte)
```

## 6. Dados de Demonstração

### 6.1 Arquitetura de Seed Data

Os dados de demonstração seguem a mesma estrutura dos dados reais, mas são armazenados em memória volátil:

```
src/
  seed/
    demo-data.ts          → Entry point
    demo-portfolio.ts     → Carteira demo (5-8 ativos)
    demo-operations.ts    → Operações demo (12 meses)
    demo-dividends.ts     → Proventos demo
    demo-goals.ts         → Metas demo
    demo-finance.ts       → Gestão Financeira demo
```

### 6.2 Princípios dos Dados Demo

| Princípio | Descrição |
|-----------|-----------|
| **Mesma estrutura** | Dados demo usam os mesmos tipos/entidades que dados reais |
| **Isolamento total** | Nenhum dado demo persiste no Supabase |
| **Determinístico** | Mesmo seed produz exatamente os mesmos dados |
| **Realista** | Valores e variações simulam comportamento real de mercado |

## 7. Feature Flags por Ambiente

### 7.1 Estratégia (estendendo ADR-017-002)

O ADR-017-002 estabeleceu a política geral R-FF-001 a R-FF-006. A PI-018 expande para contemplar ambientes:

| Flag | Ambiente | Perfil | Descrição |
|------|----------|--------|-----------|
| `DEV_MODE` | localhost | Desenvolvedor | Ativa store em memória |
| `DEMO_MODE` | Todos | Demo | Ativa dados de demonstração |
| `ADMIN_ENABLED` | Produção | Administrador | Ativa painel admin |
| `FINANCE_INTEGRATION` | Todos | Usuário | Integração Carteira/GF (ADR-017-002) |

### 7.2 Resolução de Flags

```
1. Verificar ambiente (Vercel env vars / localhost)
2. Verificar perfil do usuário
3. Verificar configuração do usuário (se aplicável)
4. Compor permissão final
```
